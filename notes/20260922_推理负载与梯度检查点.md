# 推理的两种负载 + 梯度检查点

日期：2026-09-22　阶段：训练与推理基础

## 一、推理为什么要分两段（Prefill / Decode）

| 阶段 | 在干什么 | 瓶颈 |
|---|---|---|
| **Prefill** | 一次性把整段提示词读进去，所有 token **并行**算 | **算力**（FLOPS），GPU 利用率高 |
| **Decode** | 一个字一个字往外吐，下一个必须等上一个算完 | **内存带宽** —— 每吐 1 个 token 都要把整个模型权重重读一遍 |

**数字直觉**：7B 模型 fp16 权重约 14GB，带宽 1TB/s → 光读一遍就 14ms。所以单请求生成慢不是算力不够，是"搬运"太慢（大厨手快，食材送得慢）。

## 二、Attention 为什么一直盯 KV Cache

每生成 1 个 token，都要回头把**之前所有 token 的 K/V 读一遍**：
- 缓存随上下文**线性增长** → 吃显存
- 读缓存本身也**吃带宽** → 拖慢生成

类比：每写一个字都要把前面整篇文章复查一遍 —— 越写越慢、越占地方。这正是长上下文又贵又容易爆显存的根因。

## 三、MoE：稀疏计算 + 大规模路由调度

模型里有很多"专家"子网络，但每个 token **只用其中 1~2 个**（稀疏：参数总量大，每次只激活一小部分 → 又大又快）。
代价：要有**路由**决定每个 token 去哪些专家 → token 分发出去、算完收回来（all-to-all 通信）。

类比：餐厅 8 个档口，每道菜只去一个档口做（快），但需要有人不停分单、传菜 —— 调度和通信反而成瓶颈，还会出现"某档口排长队、别的闲着"（负载不均衡）。

## 四、多模态为什么有独立 Encoder

文本、图像、音频形态不同，不能直接塞进同一个 Transformer → 各自先用 **Encoder** 翻译成同一套向量语言（图像走 ViT 切成 patch 变成一串向量），再交给 LLM 主干。

类比：不同国家的人开会，每人先配一个翻译把自己的话译成同一种语言。

**这四件事的共同结论**：优化手段完全不同 ——
| 对象 | 优化思路 |
|---|---|
| Prefill | 堆算力、做大 batch |
| Decode | 省带宽：权重量化、投机解码、批处理共享权重读取 |
| Attention / KV Cache | 管缓存：分页、驱逐、量化 KV |
| MoE | 管通信与负载均衡 |
| 多模态 Encoder | 单独调（图像 patch 多 → 又变成高并行大矩阵） |

## 五、梯度检查点（gradient checkpointing）

**是什么**：训练时每层的**中间结果（激活值）**必须留着，反向传播求梯度要用。层多、批量大时，激活值是训练显存的大头。
梯度检查点的做法：**只留少数几层的中间结果，其余全扔**；反向传播需要时，从最近的"检查点"**重新算一遍**。

**本质一句话**：**拿计算时间换显存**（多花一次前向计算，省掉大量激活显存）。

类比：看长篇小说怕忘前文 —— 不用每页都夹书签（书签比书还厚），只夹几个关键节点，需要时从最近的书签翻回去重读几页。

**还没搞懂的（下次继续）**：
1. "每隔 √n 层放一个检查点最优"是怎么推出来的
2. 重算的粒度（按层 vs 按块）对速度的实际影响
3. 和 ZeRO / 混合精度这些省显存手段叠用时的取舍
